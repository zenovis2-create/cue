# Driver targeted Stop actual-OS plan

Done means one focused Vitest uses the public `createOrchestrationDriver(...).stop(runId)` path with two concurrently active, separately approved run IDs. Each runtime launch owns a real Node controller which owns one real grandchild and emits PID plus creation-time identity before activation completes. After `stop(firstRun)`, only the first execution receives the driver cancellation signal/cancel call; its exact controller and grandchild identities are absent, while the second execution's heartbeat advances and both identities remain the originally observed processes. The sibling is then stopped through its own run ID. Final cleanup verifies every exact identity absent and removes only a canonical, non-symlink direct child of the OS temp directory. Billing/acceptance remain unknown and no provider is invoked.

Implementation/offline correction cap: 2. Actual OS test attempts: 2. Every pass runs from `daemon`: `npx vitest run --disableConsoleIntercept --reporter=verbose --fileParallelism=false --maxWorkers=1 test/integration-driver-targeted-stop.test.ts`.

The fixture will reuse the real SQLite ledger, local orchestration policy, engine, and public driver contracts from `integration-local-driver.test.ts`, but its injected runtime boundary launches owned Node processes. It will create two distinct envelopes/worktrees and immutable per-run configuration rather than mutate one run's configuration. Process termination will use the existing scoped termination API with captured PID/creation identity; it will never kill by an unverified or recycled PID. Failure retains logs and owned diagnostics, and no broad process or recursive filesystem cleanup is allowed.

Current source audit: `stop(runId)` looks up only that prepared entry, marks only it cancelled, aborts its acceptance controller, and calls `cancelActive(entry)`. Therefore a per-run route exists; the missing evidence is an actual-OS integration across this public driver boundary, not a missing production API.
