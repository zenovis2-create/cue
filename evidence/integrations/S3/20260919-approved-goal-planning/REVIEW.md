## Source assessment

Core pins prepared run phase and routes approve, execute, stop, close, and completion to the owning driver. The planning source is captured from an accepted generated output, then its exact artifact bytes, proposal hash, and current acceptance source tuple are rechecked during second approval and execution. The reader names the producer attempt explicitly, requires distinct completed clean producer/verifier attempts, checks final acceptance and the manifest's generated-output digest and size, and revalidates the proposal against the original approved input. The planning stage grants no file action; the isolated checker receives the pinned approved input and exact output bytes. No model text is treated as semantic correctness or execution success merely because the structural checker accepted it.

This is an opt-in component. `planningOrchestrationFactory` is only consumed in `app/core.mjs`; no protected startup/main construction supplies it. The UI therefore remains unavailable in the current product route without a separately qualified host selector. The Core fixture's execution host uses synthetic capability, accounting, and authority callbacks and deliberately throws at the provider boundary; it proves dispatch binding, not successful execution/publication/cleanup. The host fixture also replaces the lowest executors synthetically and makes no model/provider/network call. Planning availability intentionally requires a qualified execution host so its trusted policy/catalog can be frozen before first approval.

The negative oracles use fixture boundaries: a second legitimately accepted planning run supplies a foreign source with identical proposal bytes, and missing native cleanup observations produce an unknown cleanup result. They do not bypass immutable output tables or manufacture a final receipt. These tests support provenance and cleanup refusal for the offline host; they do not qualify live cleanup or model semantics.
