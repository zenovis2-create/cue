# Independent planning UI and IPC review

Verdict: PASS for the bounded offline UI/IPC flow. No actionable blocker found.

The new preload surface exposes planning availability, planning preparation, and conversion from a stored planning run. The IPC handlers accept only exact plain own-data commands (`goal` or `planningRunId`, autonomy, selection mode), reject extra proposal text, accessors and malformed IDs, and apply the existing trusted-sender gate before Core. Renderer text from preparation, cards, and errors is assigned through `textContent`; the new path does not inject HTML or promote rendered model text into proposal authority. Conversion sends only the planning run ID and settings to Core, which reads accepted stored output. The default control stays disabled when the host reports planning unavailable or the preload methods are absent.

The renderer offers conversion only when the planning card is completed, `readyForExecution` is true, and execution ownership is released. It requires an execution-phase response tied to that planning run, creates a new pending approval card, and requires a second approval click before launching that run. Existing general and JSON preparation remain separate. Launch and transport failures retain the prior unknown-state, stop, and polling behavior; the focused existing regressions passed.
