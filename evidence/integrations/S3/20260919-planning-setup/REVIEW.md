# Independent planning settings UI and IPC review

Verdict: PASS for the bounded offline settings flow after one test correction.

Core stores planning settings under the dedicated `goal-planning-default` ID and `goal-planning-v1` template, disabled by default. A configure call records the bounded settings and requires restart; it does not prepare a run or change the JSON template settings. Planning availability still depends on a configured and supported planning host, so saving settings alone does not enable the currently unwired product path. IPC accepts exact `read` or bounded `configure` commands through the trusted-sender gate, and rejects extra fields such as an endpoint. The renderer uses a separate settings form, displays returned identity and availability through `textContent`, and leaves preparation blocked after a restart-required response. The existing planning two-approval, JSON, and renderer transport paths remain covered by the focused regression.

My first independent five-file run had 15 passes and one failure: the exact preload surface expectation in `p11-electron-surface.test.ts` omitted the newly exposed `localPlanningSetup`. The maker updated that expectation and the exact IPC channel list without changing production behavior. I reran the same command from `daemon`: `npx vitest run test/integration-planning-setup-ui.test.ts test/integration-planning-ui-ipc.test.ts test/integration-json-template-ui.test.ts test/p10c-renderer.test.ts test/p11-electron-surface.test.ts --reporter=verbose --fileParallelism=false --maxWorkers=1`. Final result: exit 0, 5 files, 16 passes.

The new renderer test runs actual HTML and event handlers in JSDOM with mocked settings replies. The Core test uses local SQLite and verifies no task is prepared. The IPC test uses a mock sender and Core. These checks do not render Electron, start the planning host, call Qwen or a provider, or establish model qualification. Root owns the final coordinated build and wider product gate.
