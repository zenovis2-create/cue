# Independent design review: cold-start discovery

## Verdict: REVISE before implementation

The plan identifies the current gap correctly, but its single unit combines two different authorities and does not explicitly require trusted bounded monetary cost for the conservative default. Unknown performance is compatible with a default choice; unknown monetary upper bound is not. Naming a “verified” candidate cannot authorize the engine or `host.reservation()` to invent price or cost.

The smallest executable first unit should implement **conservative default only**. Persist one immutable run-bound record containing the candidate ID, selection-policy digest/revision, currency, unit, maximum per-attempt reservation units, trusted source/digest, observation time, and expiry. Bind it before engine start. The fallback may run only when ordinary ranking has no selected candidate because performance statistics are absent, the candidate remains allowed and host-eligible, the binding is current and exact, and the host reservation matches currency/unit and does not exceed the stored bound. The existing ordinary `integration_budget` reservation must still occur atomically with claim/preparation. Missing, stale, foreign, mismatched, or exhausted authority fails before preparation. The decision record must state “conservative default / performance unmeasured,” never a score or measured ranking.

Ranked usable estimates continue through the existing selector and win normally; the default is not a pin and must not override them. Replay must bind the stored default decision and ordinary budget reservation exactly. Tests need all-unknown selection, ranked-estimate precedence, missing/stale/currency/unit/upper-bound failures, ordinary-budget exhaustion, atomic rollback, hostile input, and exact replay.

**Exploration should be a later unit.** It requires separate run-bound authorization, candidate scope, limit and per-attempt upper bound, immutable reservation/settlement identity, and atomic co-reservation with the ordinary budget. The proposed “exploration allowance ledger” is not executable until its accounting semantics answer whether consumption is reserved upper units or settled actual units, how refunds/debt/revisions work, and how replay binds both records. Exploration must never replace or relax the ordinary budget; both limits must pass in the same immediate transaction. A generic allowance to choose any unknown candidate is too broad—authorization must name the candidate or a frozen bounded set and deterministic rule.

This review makes no source or test change and ran no suite. It does not approve cold-start execution, exploration, price inference, provider truth, local fixed-pair changes, Core/UI wiring, or checklist completion.
