### Role, control surface, protocol, and authentication

`stablyai/orca` is an ADE/control plane, not a model provider. Its CLI controls a running Orca runtime: worktrees, terminals, files, embedded browser state, automations, artifacts, and native tools ([overview](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/cli/overview.mdx#L12-L29)). Its experimental orchestration model separates Run, Task, and Dispatch; Dispatch owns worker placement and lifecycle completion ([orchestration](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/cli/orchestration.mdx#L7-L25)). Structured CLI output uses an `{id, ok, result, _meta}` envelope.

The local transport is newline-delimited JSON over a Unix socket or Windows named pipe, with request/response IDs, a 1 MiB frame limit, 32-connection limit, and 30-second idle handling ([transport server](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/src/main/runtime/rpc/unix-socket-transport.ts#L1-L20)). The runtime generates a random 24-byte hexadecimal shared token ([runtime state](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/src/main/runtime/runtime-rpc/runtime-rpc-state.ts#L30-L50)), publishes endpoint/token metadata, and rejects absent or invalid tokens ([admission](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/src/main/runtime/runtime-rpc/runtime-rpc-request-admission.ts#L106-L139)). On Windows the client metadata resolves under `%APPDATA%/orca` ([metadata](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/src/cli/runtime/metadata.ts#L38-L65)). Remote/mobile WebSocket pairing is a separate device-token and encrypted path; pairing can widen the listener beyond loopback ([lifecycle](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/src/main/runtime/runtime-rpc/runtime-rpc-lifecycle.ts#L65-L96)). A local runtime token is not evidence of an agent subscription or model credential.

The separate `xiws/orca` is a Go CLI that talks directly to OpenAI-compatible endpoints and exposes model-driven `read`, `write`, `edit`, and `bash` tools ([README](https://github.com/xiws/orca/blob/067d638a1c0849276dc0414db578c01dbb7f740d/README.md)). Its own documentation still lists the multi-turn session loop and write/edit approval policy as unfinished. It is not a substitute identity for `stablyai/orca` or for the local Orca runtime.

### Windows/runtime/install effects and unsupported limits

The `stablyai/orca` Windows installer and desktop updater mutate application state. First launch requests home-directory access and can import `~/.claude`, `~/.codex`, and Ghostty settings ([install docs](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/install.mdx#L46-L57)). CLI registration can create a user-writable wrapper and update the user `PATH`; the packaged Windows application includes `resources/bin/orca.exe` ([CLI installer](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/src/main/cli/cli-installer.ts#L119-L143)). Worktree commands can create/remove Git worktrees, launch agents, send prompts, and execute project or user setup hooks ([CLI reference](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/cli/reference.mdx#L80-L101)). Artifact sharing is an explicit signed-in publication action; packaged builds emit anonymous telemetry unless disabled ([telemetry](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/telemetry.mdx#L7-L19)). An adapter must not trigger imports, installation/update, device pairing, network exposure, artifact publication, telemetry changes, or global orchestration resets implicitly.

Maintenance is rapid, but the orchestration interface is explicitly experimental and flags evolve with the application. Retired commands have no effect ([orchestration limits](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/cli/orchestration.mdx#L168-L174)). Terminal handles are runtime-scoped, host scope may be unverifiable, and a bulk close does not claim success when PTY exit cannot be confirmed ([CLI reference](https://github.com/stablyai/orca/blob/2ecde717b4561cae1701a27615f704434232399a/docs/site/content/docs/cli/reference.mdx#L118-L130)). `worker_done` or a visually idle terminal is lifecycle evidence, not Cue requirement acceptance.

### Cue suitability

Keep `orca` **inactive-unresolved**. If provenance later binds an installed binary to `stablyai/orca`, a subordinate worktree/terminal/orchestration adapter is plausible: use structured argv and `--json`, require a status probe and exact worktree/terminal/dispatch IDs, separate read and mutation grants, use bounded timeouts, and retain Cue-owned acceptance and cleanup verification. Default any worktree creation path to skipping setup hooks until the user explicitly authorizes them. Do not present it as a model adapter.

Herdr is Apache-2.0 ([release-pinned license](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/LICENSE)). Redistribution is permitted subject to the license, notice retention, and marking modified files. ### Role, control surface, protocol, and authentication

Herdr is a persistent terminal workspace/runtime for coding agents, not an LLM or provider. It owns terminal panes, keeps them under a background server, and derives agent state from lifecycle integrations or terminal-screen manifests ([agent support](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/agents.mdx#L10-L50)). It exposes the same broad control surface through an agent skill, CLI wrappers, and a raw socket API. The API can create/close workspaces and tabs; split, read, send input to, and close panes; prompt/start/wait on agents; manage worktrees/integrations/plugins; subscribe to events; reload configuration; and stop the server ([socket API](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/socket-api.mdx#L6-L47)).

Transport is newline-delimited JSON over a Unix-domain socket or Windows named pipe. The installed binary can emit a JSON Schema, and the docs recommend CLI wrappers for ordinary automation and Windows portability ([transport](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/socket-api.mdx#L652-L693)). JSON clients must ignore unknown fields and handle unsupported methods; endpoint capabilities are negotiated ([stability](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/socket-api.mdx#L939-L955)).

No application token, API-key, role, or RBAC layer is documented for the local API. On Unix, the implementation creates owner-only socket directories/files ([socket paths](https://github.com/herdrdev/herdr/blob/b99002ac99b09e00b4ca692436cb15a6b0d676f1/src/server/socket_paths.rs#L555-L660)); Windows uses a named pipe, but the reviewed docs do not specify its ACL. Treat this as a privileged trusted-user local plane and require a Windows pipe-ACL review before direct raw-socket activation. Remote attach relies on normal OpenSSH authentication and can use `ssh-agent` ([remote attach](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/persistence-remote.mdx#L42-L83)).

### Windows/runtime/install effects and unsupported limits

The direct Windows installer downloads a release, stores versioned packages under `%USERPROFILE%\.herdr\packages\standalone\releases`, modifies user `PATH`, maintains compatibility aliases, and retains older versions. The archive contains `herdr.exe` plus an app-local ConPTY runtime and must remain together ([install](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/install.mdx#L16-L28), [archive](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/install.mdx#L100-L102)). Starting Herdr creates/attaches persistent local server/session state. Integration installers write hooks or plugins into agent configuration. For example, Pi installation writes `~/.pi/agent/extensions/herdr-agent-state.ts`, and Codex installation updates files under `~/.codex` and enables hooks in `config.toml` ([integrations](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/integrations.mdx#L96-L110), [Codex integration](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/integrations.mdx#L142-L152)). Plugin installation can clone GitHub sources and run author-declared build commands without sandboxing ([plugins](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/plugins.mdx#L21-L38)). An adapter must not install integrations or plugins as a discovery step.

Native Windows support is generally available, but plugins are preview/best-effort; live cwd after PowerShell `cd`, IME/cursor behavior, graphics, and clipboard-image behavior are partial or terminal-dependent. Direct terminal attach and live server handoff are unsupported on Windows ([Windows support](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/windows-beta.mdx#L58-L85), [unsupported table](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/windows-beta.mdx#L116-L135)). The same revision contains a documentation conflict: the Windows page calls saved SSH machines supported, while the connecting-machines page says multi-machine connections are not yet verified or supported on Windows ([connecting machines](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/connecting-machines.mdx#L10-L20)). Cue should treat Windows multi-machine federation as unsupported until upstream resolves that conflict.

For Codex, the integration supplies session identity while screen-manifest heuristics remain the state authority. Screen hooks can miss permission or interruption transitions; an unknown prompt can be misclassified as idle rather than blocked ([state authority](https://github.com/herdrdev/herdr/blob/9ad65d9031e8cb16a7b553c0e6f74809e9811e92/docs/next/website/src/content/docs/agents.mdx#L40-L62)). A server restart does not preserve arbitrary original processes; supported agent restoration depends on a current integration and resumable session reference. Live handoff is experimental.

### Cue suitability

Keep bare `herdr` **inactive-unresolved**, but `herdrdev/herdr` is a technically strong conditional candidate for a local terminal-agent adapter. Prefer CLI JSON wrappers, export/probe the bundled schema and capabilities, use exact session/workspace/pane IDs, set hard timeouts, and re-resolve IDs after reconnect/restart. Treat `idle`, `blocked`, waits, and notifications as advisory state. Before raw named-pipe use, resolve the Windows ACL question. Activation must not silently install/update Herdr, integrations, plugins, or remote binaries.

### Role, control surface, protocol, and authentication

PI-Desktop is an application, not primarily a headless service. Its usable external control surface is an opt-in local Streamable HTTP MCP server. With `PI_DESKTOP_MCP_CONTROL=1`, Electron Main binds `127.0.0.1`, writes a connection manifest plus persistent random 256-bit bearer token under Electron user data, and exposes named project/session/Agent/workspace flows and an explicitly reviewed desktop-operation catalog ([architecture](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/docs/spec/02-architecture/01-architecture.md#L87-L104)). The surface includes project/session operations, agent prompt/status/stop/abort/compact, Plan/Goal resolution, workspace diff, and bounded filesystem list/read; generic calls use discovery plus a reviewed invoke catalog ([implementation](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/apps/desktop/electron/main/mcp-control.ts#L275-L434)). Prompt acceptance is asynchronous, so clients poll agent status/session state; the endpoint does not offer an SSE event stream ([prompt behavior](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/apps/desktop/electron/main/mcp-control.ts#L1041-L1065)).

The server is disabled by default, loopback-only, rejects non-loopback binding, validates browser Origin, and protects requests with its bearer token. Secret get/set/delete, provider/OAuth/MCP secret writes, settings writes, and native pickers/dialogs are excluded. Dangerous/destructive operations require `confirm: true`, but that flag is the calling agent's acknowledgement and does not display a human approval prompt. The caller therefore has the running desktop user's authority for exposed operations ([security contract](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/docs/spec/05-security/01-security.md#L173-L206)). The separately documented WebSocket/HTTP RACP is a post-MVP target; it is not the current advertised remote adapter contract ([post-MVP boundary](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/docs/spec/02-architecture/01-architecture.md#L106-L119)).

### Windows/runtime/install effects and unsupported limits

Stable releases provide Windows x64 NSIS and portable executables. The packaged application bundles the Rust host and pi sidecar; building from source requires Node `>=22.19`, pnpm `>=10`, and Rust, while packaged users do not need those build tools ([requirements](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/README.md#L413-L421)). The NSIS build can perform in-app download/quit/install; the portable build avoids installation but still uses the application-data directory ([release runbook](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/docs/spec/06-delivery/06-release-runbook.md#L419-L428)). Enabling MCP adds the bearer-token manifest under Electron user data. Conversations are stored as JSONL with a SQLite index, settings/logs are local, API credentials use OS-backed secret storage, and model requests go directly to the configured provider ([local data](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/README.md#L285-L300)).

The project is explicitly Early Preview; APIs, extension interfaces, and desktop behavior may change ([status](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/README.md#L39-L43)). Current work still includes installer upgrade/rollback qualification, runtime/session recovery, stronger plugin sandboxing/publisher verification, and broader UI E2E coverage ([maintenance priorities](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/README.md#L395-L407)). Plugins remain user-trusted code rather than a complete OS sandbox ([plugin warning](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/README.md#L275-L280)). MVP expressly excludes a remote Gateway/WebUI, multi-user authentication, mobile clients, and a separate planner agent ([non-goals](https://github.com/vastsa/PI-Desktop/blob/2b1ebb9336a871688a8aee0a17a5214ed7a41a25/docs/spec/01-product/02-non-goals.md#L3-L20)).

### Cue suitability

`vastsa/PI-Desktop` is a conditional, experimental positive for a same-host MCP adapter. Its project/session/prompt/status/approval/diff surface and bearer authentication are useful, but Cue must launch or discover the full desktop only when the user has enabled MCP, protect the token manifest, version-pin the contract, poll with bounded backoff, and model `confirm: true` as delegated local-user authority. It is unsuitable as an assumed remote/headless adapter without a separately verified RACP deployment. Keep the generic `pi` basename inactive because it cannot distinguish PI-Desktop from the Pi CLI/harness or unrelated projects.
