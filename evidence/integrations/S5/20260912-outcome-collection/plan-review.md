1. **Preflight read bounds before strict readers.** `readAcceptanceHistory` reads all attempts, steps, retry links and execution receipts through `executionHistory`; its evaluation payload allowance is 16MiB and it fetches acceptance blob bytes. Monetary and local summary readers also enumerate reservations. A final one-MiB serialized-output check cannot bound these reads. Within the same snapshot transaction, first check scoped counts and aggregate/max byte lengths in SQL (including referenced blobs and nested reader inputs), and return unavailable before materializing over-limit data. Do not truncate away failed/retry rows to obtain a successful outcome.
2. **A monetary summary is not a receipt-integrity reader.** `budget.ts:snapshot` aggregates indexed receipt columns without revalidating their payload lineage. `actualUnits` starts at zero and remains zero with no known actual receipt; `committedUnits` may be reservation upper bounds. Validate the selected latest receipt's payload/index/identity semantics before claiming observed actual amounts, retain known/unknown/final coverage separately, and never label absent actual data as actual zero. Later revisions must replace the request's earlier revision in totals, not add to it. Keep local committed dispatch intents in their own nonmonetary discriminated structure.
3. **Own a committed read snapshot and resolve contradictions explicitly.** Reject an outer transaction before collecting; otherwise a caller could return a rollback-able acceptance/receipt as an actual outcome snapshot. Own the read transaction across SQL preflight, nested readers, projection and digest. A strict accepted receipt plus a conflicting parent failure/cancellation marker must remain unknown/unavailable rather than selecting whichever classification check runs first.

These points were sent to the maker during preparation; they are acceptance conditions, not claims that the unfinished implementation fails them.
