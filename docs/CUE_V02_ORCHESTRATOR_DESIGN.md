위치: `v0.2` 브랜치 `docs/` 아래. v0.1(P12) 봉인이 끝나 repo 밖 보관 사유는 소멸했다.

## 0. 한 줄 정의

v0.1 Cue = "사용자 자연어 의도 → 안전한 실행 범위 번역기 + 감시자 + 보고자" (에이전트 **1개**)
v0.2 Cue = **위 정의를 유지한 채, 실행 주체를 "로컬에 설치된 여러 툴·모델" 중에서 고르고 단계별로 인계하는 지휘자**

**바뀌지 않는 것:** 봉투, 원장, 워커 격리, 위반 즉시 봉인, writer lease, fail-closed.
**바뀌는 것:** 봉투를 발급받는 대상이 하나가 아니라 **역할별로 여럿**이 된다.

> 에이전트가 늘면 안전 장치는 덜 필요해지는 게 아니라 **더** 필요해진다.
> writer lease는 동시 writer 사고 때문에 넣었는데, 툴이 3개가 되면 그 사고가 기본값이 된다.

## 2. 뼈대 4개

### ① 툴/모델 레지스트리

| 필드 | 의미 |
|---|---|
| `name` | 툴 식별자 (codex, claude, orca, …) |
| `detected` | 실제 실행 파일이 디스크에 있는가 (**추정 금지, 경로 확인**) |
| `binarySha256` | 실행 파일 핀 — v0.1 `binaryIntegrityPinned` 재사용 |
| `models[]` | 이 툴이 부를 수 있는 모델 식별자 |
| ~~`enforcement_capable`~~ | **레지스트리에 쓰지 않는다.** §8 probe의 파생 판정 |
| `writes_capable` | 워크스페이스 쓰기가 가능한가 (툴의 기능 여부일 뿐, 허가가 아니다) |

**레지스트리는 "무엇이 있는가"만 적는다. "무엇을 해도 되는가"는 적지 않는다.**
자격은 전부 §8 probe 결과에서 **파생**된다:

- `implementationEligible = every(P1…P5)` — 쓰기 역할 배치 가능 여부
- `modelOnlyEligible` — 동적 실행 툴 없이 모델 호출만 하는가 (§8-7)

**미탐지 툴은 없는 것이다. 미측정 툴은 자격이 없는 것이다.**

### ② 역할 기반 라우팅

| 단계 | 필요 권한 | 봉투 |
|---|---|---|
| 기획 | 워크스페이스 **읽기만** | 쓰기 없음 |
| 구현 | 워크스페이스 **쓰기** | writer lease 보유, 경로 한정 |
| 검증 | 읽기 + 테스트 실행 | 쓰기 없음, 실행은 테스트 명령만 |

**단계 전환 = "봉투 수정"이 아니라 "이전 봉투 종료 + 새 봉투 발급".**
**writer lease는 단계가 아니라 워크스페이스 단위.**

### ③ 사용량 기반 대체 경로

- ❌ "API에 남은 쿼터를 물어본다" (대부분 불가능)
- ✅ **"Cue가 자기가 쓴 양을 원장에 적어서 추정한다"** → `estimated` 표기 강제
- **통화 비용 환산 금지 — 토큰 임계값만**
- 임계값 도달 = **알리고 멈춤(fail-closed)**. 자동 대체는 사용자가 미리 허용한 목록 안에서만

### ④ 인계 계약

| 항목 | 설명 |
|---|---|
| `goal` | 다음 단계가 받는 목표 (원문 보존) |
| `artifacts[]` | 이전 단계 산출물 경로 + **해시** |
| `envelope` | 다음 단계용 **새** 봉투 |
| `provenance` | 어느 툴·모델이 만들었는가 (v0.1 `orderedToolProvenance` 재사용) |

**단계 종료 게이트:** 산출물이 목표와 관련 있음을 증명해야 다음으로 넘어간다.
실패 시 다음 단계를 **시작하지 않는다.**

## 3. v0.1에서 그대로 가져오는 안전 계약 (완화 금지)

- 봉투 실행 중 수정 금지
- 금지 목록: `acceptForSession`, `acceptWithExecpolicyAmendment`, `applyNetworkPolicyAmendment`,
  permissions `scope:"session"`, yolo/bypass/`--approve-for-me` 계열, **빈 permissions 응답**
- **통화 비용 환산 금지**
- 데몬 크래시 뒤 쓰기 자동 재개 금지 → `blocked/crash`
- **타임아웃은 FAIL** (inconclusive 아님)
- **파일이 디스크에 없으면 그 주장은 존재하지 않는다**
- Electron 렌더러: `contextIsolation: true` / `nodeIntegration: false` / `sandbox: true`
- **위반 즉시 turn/tool 채널 봉인** (P12 `noPostViolationExecution`)
- **AppContainer 프로필 수명** — 띄우기 전 원장에 `appcontainer_profile_pending` 기록,
  정상 종료·stop·rollback·startup reconciliation에서 `Cue.Worker.*`만 제거
  (P12 blocker. 워커가 늘면 누수도 배로 늘어난다)

## 4. 사용자 결정 사항

### 4-1. 모델 선택 = **프리셋 + Cue 추천** (확정)

- 사용자가 프리셋을 저장한다 (예: `기획 gpt → 구현 grok → 검증 claude`)
- Cue는 추천을 **제시**한다. **자동 적용하지 않는다.**
- 추천 근거 표시: detected 여부, **P1~P5 벡터와 파생 자격**(`implementationEligible` / `modelOnlyEligible`), 사용량 `estimated` 잔여

**선:** 추천은 제안이지 실행이 아니다. 실행은 사용자 승인 = 봉투 발급 시점.

### 4-2. 재시도 = **n회 재시도 후 멈춤** (확정)

- `n`은 프리셋에 저장. 기본 제안 `n=1`
- **재시도는 같은 단계·같은 봉투 범위 안에서만.** 재시도가 권한을 넓히지 않는다
- **재시도마다 원장에 별도 시도로 기록.** 마지막 시도만 남기지 않는다
- `n` 소진 시 파이프라인 `blocked` — 다음 단계로 넘어가지 않는다
- **타임아웃은 FAIL로 센 뒤 재시도한다** (inconclusive로 세탁 금지)
- 재시도는 **같은 모델**로 (모델을 바꾸면 실패 원인이 모델 탓인지 목표 탓인지 못 가림)

## 5. 코드 상수 vs 사용자 설정 (§4-3 판단 자료)

**같은 것:** 둘 다 "단계 순서와 각 단계 담당 툴"을 담는다.
**다른 것: 누가 바꿀 수 있고, 바뀔 때 무엇이 검증되는가.**

| | 코드 상수 | 사용자 설정 |
|---|---|---|
| 변경 주체 | 개발자 (재빌드 필요) | 사용자 (앱 안에서) |
| 검증 시점 | **빌드 시** — 타입·테스트가 잡음 | **런타임** — 스키마 검증을 직접 짜야 함 |
| 잘못된 값 | 빌드 실패 = 존재 불가 | 앱에 들어옴 → **fail-closed 필요** |
| 새 파이프라인 | 코드 수정 + 릴리스 | 즉시 |
| 공격면 | 없음 | **설정 파일이 신뢰 입력이 됨** |

**핵심 위험:** 설정을 열면 **파이프라인 정의가 봉투 발급에 영향을 준다.**
설정을 고칠 수 있는 자는 "검증 단계를 빼거나", "읽기 전용이어야 할 단계에 쓰기를 주거나",
"`implementationEligible: false`인 툴을 구현 단계에 앉힐" 수 있다.
→ **설정 파일 자체가 보안 경계**가 된다. v0.1이 YAML 편집 UI를 영구 제외한 이유.

### 5-1. 결정: **사용자 설정** (user 확정)

파이프라인 정의를 사용자가 앱 안에서 바꿀 수 있게 한다.
**따라서 설정 파일은 신뢰 입력이 아니라 검증 대상이다.** 아래 6개 가드레일이 필수다.

**G1. 스키마 fail-closed.**
파싱 실패·미지의 필드·타입 불일치 = **로드 거부 + `blocked/config_invalid`**.
"모르는 필드는 무시"는 금지. 무시는 곧 조용한 권한 확대다.

**G2. 역할 권한은 설정이 아니라 코드에 있다.**
설정은 **"어느 자리에 어느 툴·모델을 앉히는가"만** 담는다.
기획=읽기 / 구현=쓰기+lease / 검증=읽기+테스트 — 이 매핑은 코드 상수.
설정 파일에 권한 필드를 쓸 수 있게 하지 않는다.

**G3. 능력 검증.**
`implementationEligible: false`인 툴을 **쓰기 역할에 배치하면 거부**. 거부 사유에 실패한 P항목을 표시한다.
`detected: false`인 툴을 배치하면 거부. 저장 시점과 실행 시점에 **각각** 검증한다
(저장 후 실행 전에 실행 파일이 사라질 수 있다).

**G4. 검증 단계 제거 금지.**
파이프라인에서 검증 역할을 **뺄 수 없다**. 최소 1개 검증 단계 강제.
"기획→구현"만 있는 파이프라인은 유효하지 않은 설정이다.

**G5. 설정 무결성 기록.**
로드한 설정의 해시를 **원장에 기록**한다. 실행 중 설정이 바뀌어도
**진행 중 파이프라인은 로드 시점 설정으로 끝까지 간다** (봉투 실행 중 수정 금지와 같은 원칙).

**G6. 편집 방식은 선택지 UI.**
YAML/JSON 자유 텍스트 편집기를 노출하지 않는다 (v0.1 제외선 유지).
드롭다운·목록에서 **레지스트리에 있는 툴·모델 중 고르는** UI.
설정 *파일*은 존재하지만 **사람이 손으로 쓰는 표면은 아니다.**

> 요약: **사용자가 파이프라인을 바꿀 수 있다. 단, Cue가 거부할 수 있다.**
> 설정을 여는 것과 설정을 믿는 것은 다르다.

## 6. `orca.ts` 재사용 여부 (§4-4 판단 자료)

**현재 `daemon/src/adapters/orca.ts` (1,634바이트, 미배선):**
```
createWorktree(name, repo)   worktreePs()
taskList(runId)   workerStop(dispatchId)   workerAbandon(dispatchId)
```

**둘은 겹치는 게 아니라 층이 다르다.**

| | orca | Cue 자체 |
|---|---|---|
| 담당 | worktree 생성, 워커 dispatch, 작업 목록 | **봉투 발급, 위반 감시, 원장, 격리** |
| 신뢰 | 외부 CLI (Cue가 검증 못 함) | Cue가 소유 |
| 정지 | `worker-stop` 요청 | **PID identity 확인 후 실제 사망 검증** |

**결정적 차이 — 정지 보증.** v0.1 stop canary는 PID·생성시각 identity를 대조해
**실제로 죽었는지**를 확인한다. orca `workerStop`은 **요청을 보낼 뿐, 죽음을 증명하지 않는다.**
`parseOrcaJson`이 제어문자를 손으로 이스케이프하는 것도 출력이 신뢰 가능한 형식이 아님을 뜻한다.

### 6-1. 결정: **추천안 채택 — 대체하지 말고 격리** (user 확정)

- ❌ orca를 오케스트레이션 엔진으로 채택하지 않는다
- ✅ **worktree 준비 같은 비보안 편의 기능만** 선택적으로 사용
- ✅ orca도 **레지스트리의 한 툴로 등록**, 자격은 **§8 probe 실측으로 판정**
- ✅ **정지·봉투·원장 보증은 전부 Cue 자체 경로 유지** — orca에 위임하지 않는다

**orca는 "동료 오케스트레이터"가 아니라 "Cue가 부릴 수 있는 툴 후보 중 하나"다.**
미배선 상태를 v0.2에서 급히 배선할 이유는 없다.

## 8. 자격은 선언이 아니라 측정이다 (v0.2 첫 작업)

### 8-1. 문제

현재 `daemon/src/adapters/registry.ts` 전문(115바이트):

```ts
export const adapterRegistry = Object.freeze([
  Object.freeze({ name: 'codex', enforcement_capable: false }),
]);
```

`enforcement_capable`은 **하드코딩된 리터럴**이다. 아무도 측정하지 않았다.
v0.1에서는 툴이 하나뿐이라 무해했다. v0.2에서는 이 필드가
**"이 툴에 구현 단계를 맡겨도 되는가"** 를 결정한다.

→ 레지스트리에 `true`라고 적는 순간, 검증 없이 권한이 생긴다.
→ 그리고 §5 결정에 따라 **레지스트리 근처에 사용자 설정이 들어온다.**
   선언값을 믿는 구조에 사용자 입력을 연결하면, 설정 파일이 권한 부여기가 된다.

### 8-2. 원칙

**적어둔 값은 능력이 아니다. 측정된 값만 능력이다.**

- `enforcement_capable`은 레지스트리에 **쓰지 않는다** (필드 제거)
- 대신 `probeEnforcement(tool)` 의 **결과**로만 얻는다
- **측정이 없으면 `false`** — fail-closed. "모르면 못 맡긴다"
- 측정 결과·시각·툴 지문을 **원장에 기록**

### 8-3. probe가 실제로 확인해야 하는 것

v0.1이 codex에 대해 실측으로 확보한 보증만 항목화한다.
**추론 금지. 각 항목은 실행해 보고 관측한 결과여야 한다.**

| # | 항목 | 실패 시 |
|---|---|---|
| P1 | **정지 증명** — stop 요청 후 대상 프로세스가 실제로 죽는가. PID+생성시각 identity로 확인 | `false` |
| P2 | **격리 경계** — `BoundaryContract.v1` 적합(§8-3a). 자기신고 금지, 전 조항 실측 | `false` |
| P3 | **부모 사망 전파** — 감독 프로세스를 hard kill 했을 때 자식이 남지 않는가 | `false` |
| P4 | **위반 봉인** — 봉투 밖 행위 관측 후 후속 실행이 차단되는가 | `false` |
| P5 | **출력 파싱 안정성** — 구조화 출력이 표준 파서로 읽히는가 (수동 이스케이프 의존 아님) | `false` |

**5개 전부 통과해야 `true`.** 하나라도 미확인이면 `false`.

### 8-3a. `BoundaryContract.v1` — P2를 AppContainer에 묶지 않는다

P2를 Windows AppContainer로 고정하면 **그 기술을 쓰는 툴만 통과**한다.
그렇다고 "경계를 제공·회수한다"는 **자기신고를 PASS로 받으면 안 된다.**
→ Cue가 소유하는 **버전형 적합성 계약**으로 추상화하고, 전 조항을 실측한다.

**공통 불변식 (backend 무관, 전부 관측 필수)**

| # | 조항 | 관측 방법 |
|---|---|---|
| B1 | 봉투 밖 filesystem 쓰기 **거부** | 봉투 밖 경로에 실제 쓰기 시도 → 거부 관측 |
| B2 | credential / environment **격리** | 부모 환경의 표식 값이 경계 안에서 보이지 않음 |
| B3 | **선언된 egress 경계** | 선언 밖 목적지 접근 시도 → 차단 또는 봉인 관측 |
| B4 | **외부 관찰 가능한 boundary identity** | 경계에 외부에서 조회 가능한 식별자가 있음 (내부 자기보고 아님) |
| B5 | 정상 · stop · **crash** 후 **잔여물 0** | 세 경로 각각 실행 후 프로세스·경계 잔여 0 |

**backend별 conformance (해당 backend일 때 추가 실측)**

- **AppContainer**: SID 파생 ACE 부여·회수, `Cue.Worker.<32 hex>` 프로필 생성·정리, live-owner 보호

**B5가 핵심이다.** v0.1의 profile leak은 정상 경로에서는 보이지 않았고
**hard kill 경로에서만** 드러났다. crash 경로를 빼면 같은 결함을 다시 통과시킨다.

### 8-4. 측정 대상은 툴 하나가 아니라 **조합**이다

"codex는 안전한가"는 **답할 수 없는 질문**이다.
경계를 세우는 것은 툴이 아니라 **Cue의 강제 코드와 boundary provider**이기 때문이다.

측정 단위 = **`measurementSubject`**

| 구성요소 | 지문 |
|---|---|
| tool binary | 실행파일 SHA-256 |
| adapter | 어댑터 소스 해시 |
| **Cue enforcement 코드** | 강제 경로 소스 해시 |
| boundary provider / policy | provider 식별자 + 정책 해시 |
| OS build | OS 빌드 번호 |

- 결과는 **P1~P5 벡터**로 저장한다 (단일 boolean 아님)
- 자격은 파생만 한다: **`implementationEligible = every(P1…P5)`**
- **어느 구성요소든 지문이 바뀌면 즉시 미측정 상태로 되돌린다** → 자격 `false`
- §5 G3(저장 시점·실행 시점 이중 검증)이 여기에 걸린다

**벡터로 저장하는 이유:** "왜 못 쓰는가"에 답할 수 있어야 한다.
`false` 하나만 남기면 사용자는 원인을 모르고, 우리는 나중에 기준을 낮추고 싶어진다.

### 8-5. 능력이 없는 툴을 어떻게 쓰는가

`enforcement_capable: false` = **쓸 수 없다**가 아니다. **구현 자리에 앉힐 수 없다**이다.

| 자리 | 요구 |
|---|---|
| 기획 / 요약 / 검증 의견 | **`modelOnlyEligible`** (§8-7 — "안 쓰니 안전"이 아니다) |
| **구현 (쓰기 권한)** | **`implementationEligible`** = every(P1…P5) |

→ 사용자가 프리셋에서 능력 없는 툴을 구현 자리에 놓으면,
   **저장은 되지만 실행 시점에 Cue가 거부**한다 (§5 G3).
   거부 사유에 **어느 probe 항목이 실패했는지** 표시한다.

### 8-6. 자기 자신에 대한 정직성

현재 codex는 `enforcement_capable: false`로 적혀 있다.
**probe를 돌리면 이 값이 바뀔 수 있다.** 그래도 결과를 그대로 받는다.

v0.1의 한계 4건(P3-16 등)은 **"탐지 후 정지"이지 syscall 차단이 아니다.**
probe P4가 이 구분을 그대로 반영해야 한다 —
**"차단했다"가 아니라 "관측 후 봉인했다"가 통과 기준이다.**
이 기준을 올려 잡아 `false`가 나오는 것은 정상이며,
**기준을 낮춰 `true`를 만드는 것은 §5.2.1이 금지한 바로 그 행위다.**

### 8-7. 읽기 역할도 무조건 안전하지 않다 — `modelOnlyEligible`

"기획·검증은 파일을 안 쓰니 안전하다"는 **틀렸다.**
읽기 역할에 앉은 툴이 **자체 셸·코드 실행·네트워크 기능**을 갖고 있으면,
Cue가 쓰기 권한을 안 줬어도 **툴이 스스로 부작용을 낸다.**

→ 쓰기 자격과 **별개의 계약**을 둔다.

**`modelOnlyEligible`** = 다음이 전부 실측 확인될 때만 `true`

| # | 조항 |
|---|---|
| M1 | 동적 실행 툴(셸·코드 실행·임의 프로세스 기동) **부재 또는 비활성 강제** |
| M2 | 파일 쓰기 경로 부재 (읽기 전용 마운트/권한으로 실증) |
| M3 | 선언되지 않은 egress 부재 |

| 자리 | 필요 자격 |
|---|---|
| 기획 / 요약 / 검증 의견 | **`modelOnlyEligible`** (능력 불요가 아니다) |
| 구현 (쓰기 권한) | **`implementationEligible`** = every(P1…P5) |

**둘 다 `false`인 툴은 레지스트리에 있어도 어느 자리에도 앉지 못한다.**
