# Phase 5 — 감시자와 복구 (P5-1 ~ P5-12)

Phase 4.5까지 기동 경로가 봉인됐다(테스트 83 통과 / 3 스킵, 우회로 0).
Phase 5는 **작업이 막혔는지 판단하고, 안전하게 다시 시도**하는 층이다.

여기서 가장 위험한 실패는 **"멋대로 되살리는 것"**이다.
감시자는 무엇을 할 수 있느냐보다 **무엇을 절대 하지 않느냐**로 정의된다.

## 구속력 있는 전제 (실측, 바꾸지 마라)

1. **파일시스템 봉투는 강제, 네트워크 봉투는 탐지 + 즉시 중단.** (P3B/P3C 실측)
2. **`worker-read`는 감사 원장이 아니다** — oversized 레코드를 skip/clip한다.
   신호원으로는 쓰되, **진실의 근거로 쓰지 마라.**
3. **승인 1건 ≠ 실행 1건.**
4. 워커 기동은 소유 경로 하나뿐이다. **새 기동 경로를 만들지 마라.**
5. **통화 비용 환산 금지.** 토큰 임계값만.

## 만들 것

### P5-1 결정론적 신호 수집기
- 신호원: `gate-list`, exit code, terminal wait, `worker-read`, `task-list`.
- 각 신호를 **`conclusive`(결론) / `candidate`(후보)** 로 태깅한다.
- 출처 등급 규칙: 결정적 시스템 관측(`gate-list`, `exit-code`, `task-list`)만 `confirmed`로 취급하며, 모델/화면 해석(`terminal-wait`, `worker-read`)은 `candidate`다. `candidate`는 단독으로 사실 확정이나 상태 전이를 일으킬 수 없고, 둘 이상의 독립 후보가 모여도 진단 입력일 뿐 `confirmed`로 승격되지 않는다.
- 검사: 각 신호가 올바른 등급으로 태깅된다.
- exit code와 gate 상태는 결론이 될 수 있다. **`worker-read` 텍스트 추론은 후보다**
  (전제 2 — 잘려나간 로그로 결론을 내면 거짓말이 된다).

### P5-2 2신호 에스컬레이션
- **후보 신호 하나만으로는 LLM 진단기를 호출하지 않는다.**
- 검사: 호출 카운터 테스트 — 후보 1건 주입 시 진단기 호출 0회, 2건 시 1회.

### P5-3 정지 규칙
- `빈 페이지 + 임계 초과 + 워커 생존` **세 조건 전부**일 때만 `blocked/idle`.
- 검사: 세 조건 중 **하나만 빠져도 전이하지 않는다**(3개 음성 테스트 + 1개 양성).

### P5-4 태스크 유형별 `idle_threshold`
- 유형별 임계값이 **스펙(데이터)으로 기록**된다.
- 검사: **전역 상수 하나로 판정하는 코드 경로가 없다**(소스 검사 + 동작 테스트).

### P5-5 복구 사다리 4단
- 각 단이 원장에 **attempt 행**을 남기고, 재시도마다 **새 가설 필드**가 채워진다.
- 재시도 상한 도달 시 **4단(에스컬레이션 = 사람에게)**으로 간다.
- 검사: attempt 계보 조회 + 상한 도달 시 4단 전이.

### P5-6 3단 보존 규율 ★
- base SHA 기록 / 재시작 전 **diff 해시 아티팩트** / **fence-before-restart**.
- **검사: 재시작 경로에 `git reset` / `checkout --` / `clean -fd` / discard 호출이 없다**
  (`src/` 소스 grep 테스트 + 동작 테스트).
- 동작 테스트: 워커 작업물이 있는 상태에서 재시작을 돌리고 **작업물이 그대로 남는지** 확인.
  이건 문자열 검사만으로 끝내지 마라. 실제로 파일이 살아남아야 한다.

### P5-7 자동 도구 handoff 없음, 스키마만
- handoff-package **스키마는 정의**하되 **자동 실행 경로는 없다.**
- 검사: 스키마 검증 테스트 + "handoff를 실행하는 함수가 존재하지 않음" 소스 검사.

### P5-8 decision gate 자동 승인 금지 ★
- gate가 열리면 **항상 사람에게 간다. 자동 응답 경로 없음.**
- 검사: **자율성 ③에서도 같은 테스트가 통과한다.**

### P5-9 자율성 3수준이 실제로 다른 동작을 낸다
- ① 첫 막힘에서 정지 / ② 기계적 복구만 / ③ 새 가설 재시도·접근 교체·재분해.
- 검사: **같은 실패를 주입했을 때 세 수준의 attempt 계보가 서로 다르다**(테스트 3개).
- 검사: **①에서 복구 시도가 0건이다.**

### P5-10 자율성은 봉투를 넓히지 못한다 ★
- 검사: ③에서 봉투 밖 요청 → 여전히 `decline`.
- 검사: ③의 재분해가 `goal`/`constraints`/`done_when`/`deliverable`을
  **수정하는 코드 경로가 없다**(소스 grep + 테스트).
- 검사: **③이 재시도 상한을 올리지 않는다.**

### P5-11 실행 중 자율성 변경은 낮추기만
- 실행 중 **상향 요청 거부** → "멈추고 새 실행" 경로로.
- **하향은 즉시 발효**되고 원장에 남는다.

### P5-12 자율성 수준은 `run_id`마다 원장에 기록
- 검사: 실행 레코드에서 그 실행에 적용된 수준을 조회할 수 있다.
