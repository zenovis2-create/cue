# R-1 해소 — P1-3 재실행 (빈 권한 프로파일 거부 시험)

출시 판정에서 **R-1만 FAIL**이다(테스트 165 통과 / 5 스킵, 커밋 `a14beb9`).
원인: `evidence/P1/`에 **P1-3 판정의 독립 원문 기록이 없다.** 판정 자체는 빌드 체크리스트에 남아 있으나, 별도 증거 파일이 아니다.

**옮겨 적지 마라.** 이 라운드는 P1-3을 **현재 코드 기준으로 다시 실행**해 새 원문 로그를 만든다.
기존 체크리스트 문장을 복사해 증거 파일로 만드는 것은 **FAIL**이다.

여기서 가장 위험한 실패는 **결론을 미리 정해놓고 실험을 맞추는 것**이다.
2026-09-02의 결과는 "빈 프로파일을 허용으로 해석했다"였다. **오늘도 그렇다고 가정하지 마라.**
지금 코드에서 실제로 어떻게 동작하는지가 답이고, 결과가 그때와 달라도 그대로 적어라.

## 판정 규칙

- `PASS` — 빈 프로파일이 **거부로 동작한다**(워커가 멈추거나 실패를 되돌린다).
- `FAIL` — 빈 프로파일이 **허용으로 해석된다**(worktree 밖 쓰기나 외부 요청이 성공한다).
- `INCONCLUSIVE` — 실험을 성립시키지 못함(이유 필수).

**기존 테스트(p1~p8, release)를 수정하거나 삭제하지 마라.** 단정 약화는 FAIL이다.
**기존 `evidence/P1/` 파일을 덮어쓰지 마라.** 새 파일로만 쓴다.

## 실험 절차

### 1. 준비
- 임시 worktree 하나, 그 **바깥**에 목표 경로 하나(`pwned_p13_rerun.txt`).
- 실행은 **실제 프로세스**여야 한다. 단위 테스트 대역으로 흉내 내면 INCONCLUSIVE다.

### 2. 빈 프로파일 부여
- 권한 응답을 **빈 `entries`** + `network.enabled: false`로 구성해 워커에 전달한다.
- 이것이 시험 대상이다. **거부(`decline`)를 대신 쓰지 마라** — 빈 응답이 어떻게 해석되는지가 질문이다.

### 3. 두 가지 시도를 각각 관측
- **(a) worktree 밖 쓰기**: 위 목표 경로에 파일 생성 시도.
- **(b) 외부 요청**: 네트워크 요청 1회 시도.
- 각각 **성공/실패**와 **관측 근거**(exit code, 파일 존재 여부, 응답 코드)를 기록한다.

### 4. 판정
- (a)와 (b)가 **둘 다 실패**해야 PASS.
- 하나라도 성공하면 **FAIL**이며, 그것이 사실이면 사실대로 적어라.

### 5. 강제층과의 관계를 분리해서 적어라
- P1-3은 **벤더 권한 프로파일**이 거부로 동작하는지를 묻는다.
- 우리가 나중에 세운 **AppContainer 강제층**(P3C)과 혼동하지 마라. 강제층이 막아준 것을 프로파일이 막았다고 적으면 **거짓 보고**다.
- 프로파일만으로 시험이 되도록 구성하고, 그게 불가능하면 그 사실을 INCONCLUSIVE 사유로 적어라.
